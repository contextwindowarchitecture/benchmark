## 1. Purpose and authority

This document defines the reusable architecture, visual language, interaction model, and quality gates for current and future projects. Optimize for understandable interfaces, reliable data, accessibility, and maintainable code—not maximal animation or maximal dependency count.

MUST indicates a requirement. SHOULD indicates a default that can be changed with a documented reason. MAY indicates an optional capability.

- Agents and contributors MUST read this file, the project's package manifest, generated UI components, and applicable architecture decisions before implementing UI.
- Existing projects MUST migrate incrementally. Do not replace a working framework, router, or component primitive merely to conform to a greenfield default.
- Project-specific choices belong in `docs/design/project-profile.md`. Record significant deviations in `docs/adr/`; reference them from the profile. In this repository the results UI is parked, so its profile is drafted inside `docs/plans/ui-plan.md` (local, git-ignored) and moves to `docs/design/project-profile.md` when UI work starts.
- Security and platform constraints override visual preferences. Explicit project decisions override defaults but cannot silently remove accessibility or cleanup requirements.
- Dependency versions MUST be verified together, pinned through the project's package manager and lockfile, and updated deliberately. This document intentionally does not freeze package versions.
- A change to this baseline MUST include a migration note (section 17) and relevant tests. Do not silently redesign existing products when updating this document.

## 2. Baseline stack

### 2.1 Required capabilities

| Capability | Default | Boundary |
| --- | --- | --- |
| UI runtime | React with strict TypeScript | React owns declarative UI and component state. |
| Application framework | Vite for a client-side dashboard; Next.js when server rendering, server routes, or public SEO justify it | Choose one framework and its compatible router; do not install both by default. |
| Styling | Tailwind CSS and semantic CSS custom properties | CSS owns layout, responsive behavior, theme, and routine interaction states. |
| Components | shadcn/ui components generated into the repository | These are owned source components, not a universal layout engine. Preserve their accessibility behavior. |
| Static icons | Lucide React | Use icons for controls; pair icon-only buttons with accessible names. |
| Class composition | The `cn` utility and dependencies generated by the selected shadcn template | Retain the template's compatible class merging and variant utilities. |
| Routing | Framework router; React Router for the Vite default | Route definitions also drive navigation metadata and active states. |
| Validation | The producer's published JSON Schemas where they exist (2.3); Zod for URL state and for contracts nobody publishes | Validate untrusted input at application boundaries, not in chart rendering. |
| Formatting | Native `Intl` APIs | Centralize locale, number, currency, date, and timezone formatting. |
| Quality tooling | ESLint, formatter, TypeScript checking, component tests, end-to-end tests | CI is the enforcement mechanism. |

Tailwind v4 projects SHOULD use the current shadcn-generated CSS-first setup and `tw-animate-css` where required by generated components. Do not prescribe `tailwindcss-animate` for new v4 projects. Keep a supported v3 project on its compatible configuration until a deliberate migration. [1]

Do not mix primitive-specific APIs from different shadcn presets. Inspect the generated component: composition APIs such as `asChild` and `render` depend on the selected implementation. Do not bulk-install unused components.

### 2.2 Available specialist tools

| Tool | Role | Load policy |
| --- | --- | --- |
| GSAP + `@gsap/react` | Coordinated timelines, chart reveals, deliberate multi-element sequences | Use only where CSS is insufficient; keep it out of routes that do not need it. |
| D3 modules | Scales, extents, geometry, layout algorithms, data-to-coordinate mapping | Prefer focused imports; default to React-rendered SVG. |
| `@lottiefiles/dotlottie-react` | Optional authored illustrations and status embellishment | Lazy-load where appropriate; never require it for navigation or core status comprehension. |

Owning these tools does not mean every screen must use them. GSAP's React hook supports scoped animation cleanup; delayed animations and event-handler animations require context-safe handling. [2]

### 2.3 Conditional additions

These are architectural recommendations, not prerequisites to install indiscriminately.

| Need | Preferred addition | Decision rule |
| --- | --- | --- |
| Client-side remote data caching | TanStack Query | Use for remote queries, invalidation, mutations, cancellation, and background refresh; avoid a second cache for data already owned by a framework's server-data strategy. |
| Nontrivial forms | React Hook Form with a compatible Zod resolver | Add when validation, field state, or repeated form patterns justify it. |
| Complex data tables | TanStack Table | Add for sorting, filtering, selection, or pagination; simple tabular content can use semantic HTML. |
| Large lists or tables | TanStack Virtual or an equivalent tested virtualizer | Add after measuring the cost of rendering; preserve accessible interaction. |
| Shared client-only state | Zustand | Add only when local state, URL state, and small contexts are insufficient. |
| Next.js theme persistence | next-themes or a project adapter | Use one theme owner; do not duplicate theme state. |
| Component tests | Vitest + React Testing Library for the Vite baseline | Existing projects may retain an equivalent runner. |
| Browser and accessibility checks | Playwright plus an axe integration | Combine automated checks with keyboard and screen-reader testing. |
| Component reference catalog | Storybook | Useful for a shared system; optional for small projects. |
| Date arithmetic/timezone workflows | A maintained date library | Native `Intl` formats dates but is not the entire date arithmetic layer. |
| Data published as JSON Schema by its producer | TypeScript types generated from those schemas, and a JSON Schema validator (for example Ajv) at the boundary | Prefer the producer's schemas to a hand-written duplicate, which drifts; keep Zod for what the producer does not describe. |
| Row files too large for the main thread | A line-delimited parser in a Web Worker, with pre-aggregation | Add once a file crosses the row budget in the project profile (6.4); never load such a file whole for a summary view. |

Do not add Redux, a second animation framework, a second component system, an event bus, or a second chart library without an explicit need and decision record.

## 3. Ownership and separation

```text
Framework / router / data adapters
                 |
        Validated view models
                 |
   React + shadcn components
   CSS / Tailwind / design tokens
           |              |
   D3 computations    Optional Lottie player
           |
   React SVG / isolated renderer
           |
   Optional GSAP property-level animation
```

### 3.1 Ownership rules

- React MUST own the default DOM and SVG node lifecycle. D3 SHOULD return scales, coordinates, and path strings, not append nodes into React-owned children.
- For exceptional imperative D3 rendering, give D3 an isolated subtree with no React-managed descendants. Use keyed joins; remove listeners and simulations on teardown. Do not clear and reconstruct the chart on every refresh.
- GSAP MUST NOT independently create or remove React-controlled content. It may temporarily animate explicitly assigned presentation properties on refs.
- One owner per animated property per element: CSS and GSAP can coexist, but MUST NOT simultaneously animate the same `transform`, opacity, size, or SVG attribute.
- Lottie owns animation rendering inside its player surface. React owns its wrapper and semantic status text. GSAP may drive the controller, not the player's internal render nodes.
- Use real semantic HTML. A Card is not automatically a button, a landmark, or a heading.
- Do not store remote query results in a second global state store. Do not infer authorization from hidden navigation items.

### 3.2 CSS versus GSAP

CSS is the default for hover, focus, pressed, color, shadow, simple disclosure, and component-provided transitions. Preserve generated shadcn state animations unless deliberately replacing them.

GSAP is for choreography, controlled sequences, and chart motion that benefits from a timeline. Do not require all cards to stagger on every mount. Default dashboards should be usable immediately; background refresh must not replay page entrances.

Default motion tokens are project policy:

| Token | Default | Usage |
| --- | --- | --- |
| Fast | 120 ms | Simple feedback |
| Standard | 180 ms | Routine state transition |
| Emphasis | 280 ms | Optional entrance or short sequence |
| Maximum routine stagger | 30 ms per item; 300 ms total added delay | Small, intentional groups only |

Prefer transform and opacity for decorative motion. Do not animate layout for large collections. Do not use ScrollTrigger as a default dashboard navigation mechanism.

### 3.3 GSAP lifecycle

- Prefer `useGSAP` with a scope ref; register the hook once in the animation module or before use.
- State-dependent effects SHOULD specify dependencies and `revertOnUpdate: true` when replacement is intended.
- Use `contextSafe` for animations created later by events, timers, or callbacks.
- Context cleanup does not replace cleanup for manually added DOM listeners, observers, timers, subscriptions, or non-GSAP resources.
- Route changes and React Strict Mode MUST not leave duplicate timelines or ScrollTriggers.
- Respect reduced motion at runtime. Use `gsap.matchMedia()` or a shared reactive media-query hook; revert match-media contexts on teardown.
- Do not animate invisible initial styles unless there is a reliable no-script/no-animation fallback. Content must not depend on a timeline completing to become usable.

These hook and cleanup requirements follow GSAP's React integration guidance. [2]

### 3.4 Chart motion

D3 `.transition()` SHOULD NOT be used in the default React chart path because GSAP is the designated imperative motion owner. Static charts and CSS-owned hover states do not need GSAP.

Do not assume arbitrary SVG path strings can safely morph through `attr: { d: nextPath }`. Point count and segment topology may change. Prefer direct geometry replacement, a carefully owned crossfade, or a separately approved path-morph implementation.

For line reveal, measure the actual path using `getTotalLength()`. Never hard-code an arbitrary dash length. Do not use reveals for every polling update.

When the data records a process step by step (a budget sweep's frames, an assembly timeline's events), the animation is a scrub over the recorded steps, not an easing between two states. Each frame shown is a real recorded state; the control is a slider with play and pause, operable from the keyboard; the current step's values are readable as text; and a GSAP timeline, if one is used, maps time to the frame index and nothing else. Reduced motion shows the final frame with the slider still available. Steps the source marks as inferred render differently from exact ones (dashed, and labeled), and where an exact source exists for the same process it is preferred.

## 4. Global dashboard pattern

### 4.1 Default shell

Yes: establish one shared dashboard shell. Use a collapsible left sidebar plus a top utility header, not competing sidebar-only and navbar-only layouts per page. Marketing pages, authentication pages, full-screen editors, and embedded views may use explicitly named alternate shells.

```text
DashboardShell
├── SkipLink
├── SidebarProvider
│   ├── AppSidebar
│   │   ├── Brand / optional workspace switcher
│   │   ├── Primary navigation
│   │   ├── Secondary navigation
│   │   └── Account / settings
│   └── SidebarInset
│       ├── AppHeader
│       │   ├── Sidebar trigger
│       │   ├── Breadcrumbs
│       │   └── Search / theme / account utilities
│       └── main#main-content
│           └── DashboardPage
│               ├── PageHeader
│               ├── FilterBar (optional)
│               ├── Status / freshness region
│               ├── MetricGrid (optional)
│               └── ContentGrid / table / task view
└── Toast region / application overlays
```

Use the generated shadcn `SidebarProvider`, `Sidebar`, `SidebarInset`, and `SidebarTrigger` where compatible. The documented sidebar supports icon collapse and separate mobile state; the inset variant requires `SidebarInset`. [3]

### 4.2 Responsive behavior

The following are project defaults, not claims that shadcn supplies these exact measurements automatically. Align generated sidebar media queries with these settings.

| Viewport | Navigation | Content |
| --- | --- | --- |
| Below 768 px | Off-canvas sidebar using an accessible sheet; closed by default | Single column; page actions wrap; charts retain labels or provide a compact equivalent. |
| 768–1023 px | Compact/icon sidebar initially, user-expandable | Two-column metrics when legible; do not force narrow chart cards. |
| 1024 px and above | Expanded sidebar initially, user-collapsible | Four-column metrics where useful; content follows task priority. |

- Expanded sidebar target: 16 rem. Collapsed target: approximately 3–3.5 rem, matching the generated implementation. Header target: 3.5 rem.
- Page padding: 1 rem on small screens, 1.5 rem on medium screens, 2 rem on large screens. Default gap: 1–1.5 rem.
- Standard readable content width: up to 90 rem. Data-heavy pages MAY opt into full width via a named layout variant.
- Keep document scrolling as the default. The sidebar may scroll independently. Tables may have a labeled horizontal scroll region; the entire page must not overflow horizontally.
- Header SHOULD be sticky, not a collection of independently fixed controls. Define overlay layering centrally and account for sticky content when navigating to anchors.
- Persist desktop sidebar preference separately from mobile sheet state. Never reopen a mobile overlay simply because desktop navigation was expanded.
- Closing a mobile sheet restores focus to its trigger. Route selection closes the mobile sheet. Collapsed icon navigation retains accessible names and usable tooltips.
- Prefer CSS breakpoints. Browser-only width checks must not create server/client hydration mismatches.

### 4.3 Navigation contract

Use a typed central navigation configuration with stable IDs, labels, routes, icons, groups, and optional permission metadata. Active navigation uses router matching, not brittle substring checks. Set `aria-current="page"` on the active link.

The top header contains global utilities. The page header contains one page title, concise description, and page-specific actions. Avoid duplicate account menus, duplicate primary actions, and dashboard pages with multiple competing navigation bars.

Breadcrumbs reflect hierarchy, not a history trail. Router transitions SHOULD move focus to the new page title or main region and update the document title. Respect browser back navigation and avoid resetting task state unnecessarily.

### 4.4 Reusable page contracts

```ts
import type { ReactNode } from "react";

export type DashboardPageProps = {
  title: string;
  description?: string;
  actions?: ReactNode;
  filters?: ReactNode;
  status?: ReactNode;
  width?: "standard" | "wide";
  children: ReactNode;
};

export type MetricStatus = "pass" | "fail" | "info" | "na";

export type MetricDefinition = {
  id: string;
  label: string;
  unit: string;                // "rate", "count", "ms", "bytes", "exponent", ...
  value: number | null;
  formattedValue: string;
  numerator?: number | null;   // a rate shows its fraction beside the percentage
  denominator?: number | null;
  target?: number | null;
  status?: MetricStatus;       // the producer's judgment against target; the UI never recomputes it
  comparison?: {
    label: string;             // what it is compared with: a period, a previous record
    formattedChange: string;
    direction: "up" | "down" | "flat";
    sentiment: "positive" | "negative" | "neutral";
  };
  helpText?: string;
};
```

Direction and sentiment are distinct: a higher expense can be negative even though the arrow points up. Metric cards MUST identify comparison periods and units. Missing values render as “Not available,” not fabricated zeroes. When the producer judges a metric, the card shows that judgment and its target: `info` is measured but not gated and must not look like `pass`; `na` (a null value) was not measured in this record. A rate shows its fraction beside the percentage, so a reader can tell 1/1 from 1,000/1,000.

## 5. Design tokens and visual language

- Semantic CSS variables are the source of truth. Tailwind utilities reference them; chart adapters and canvas renderers consume the same tokens.
- Maintain generated shadcn tokens for background, foreground, card, popover, primary, secondary, muted, accent, destructive, border, input, ring, sidebar, and chart series.
- Add explicit success, warning, and info pairs; define foreground/background pairs for every status. Do not make `primary` synonymous with “success.”
- Define the status vocabulary once, with one token pair per status the data can carry: outcome statuses (`pass`, `fail`, `partial`, `error`), judgment statuses (`info`, `na`, not run) and change verdicts (`baseline`, `unchanged`, `changed`, `regressed`). Map them to the semantic pairs centrally. `info` must not look like `pass`, `partial` must not look like `fail`, and not run is muted, never red. Every status badge carries text or an icon as well as color.
- Define light and dark themes, radius, typography, spacing, motion, and overlay layers centrally. Do not invent an undefined “CWA” palette.
- Use a 4 px spacing rhythm as the default policy: 4, 8, 12, 16, 24, 32, 48. Borders, typography, optical corrections, and accessible control sizing are valid exceptions. Not every Tailwind utility is inherently a multiple of 4 px.
- Use a neutral surface hierarchy, one primary accent, limited shadows, and visible focus rings. Avoid gradient backgrounds and decorative texture by default.
- Default body size: 1 rem; supporting metadata: 0.875 rem; primary page heading: 1.5–2 rem. Dense tables may be compact but must stay readable.
- Use tabular numerals for metrics and numeric columns. Align numbers consistently; specify units and precision through shared formatters.
- Use explicit literal Tailwind class strings or variant maps. Do not generate arbitrary class names dynamically from data.
- React SVG uses `className`; imperative D3 uses `.attr("class", "...")`, not `.attr("className", ...)`.
- CSS examples: `stroke-primary`, `fill-none`, or `stroke-[var(--chart-1)]`. Canvas cannot use class names: resolve theme tokens through a central adapter and redraw when the theme changes.
- Never encode a chart series exclusively by red/green color. Include legend labels and, where necessary, line styles or symbols.

For Tailwind v4, extend the generated stylesheet's semantic mapping rather than replacing its theme configuration wholesale. [1]

## 6. Data, state, and forms

### 6.1 State ownership

| State | Owner | Examples |
| --- | --- | --- |
| Remote/server state | Chosen query or framework data layer | Records, aggregates, permissions returned by the server |
| Shareable page state | Validated URL parameters | Date range, sort, search, pagination, selected view |
| Local UI state | Component state | Open dialog, hovered point, expanded section |
| Shared client preference | Small context or optional Zustand store | Density, theme preference, desktop sidebar preference |
| Form state | Form controller | Values, touched state, validation errors |

A global interceptor is not a state-management strategy. If an API client is needed, centralize request configuration, safe error normalization, authentication integration, and cancellation there. Do not intercept requests to trigger arbitrary UI events.

### 6.2 Data pipeline

```text
Request → boundary validation → normalized domain data
        → pure selectors / aggregation → typed view model
        → React presentation → D3 geometry → optional motion
```

- Fetch outside presentational chart components. Expose typed data, status, and callbacks through props or a dedicated feature controller.
- Query keys MUST include the record's identity and version, validated filters and, where the application has identity, the tenant/user scope. Clear or partition caches on identity changes; avoid cross-tenant data leakage. Immutable records (a published run, a content-addressed artifact) are cached for the session and never refetched; only indexes refresh.
- Honor abort signals and protect against stale results overwriting newer filter requests.
- Memoize expensive geometry based on data, dimensions, domain settings, and relevant formatting inputs—not only the array identity. Avoid premature memoization of cheap calculations.
- Define freshness, retry, polling, and invalidation by feature. Pause unnecessary background work when a page is hidden, where the data strategy allows it.
- Filter changes update all related dashboard panels consistently. Label previous results as stale/updating rather than silently presenting them as current.
- Date ranges MUST declare timezone and boundary semantics. Prefer unambiguous timestamps at API boundaries. Do not silently aggregate UTC timestamps as local days.
- Mutations distinguish pending, success, failure, and rollback. Disable duplicate submission without blocking unrelated actions.
- Validation errors appear by the field and in an accessible summary when appropriate. Toasts are not the only feedback channel.

### 6.3 Required page states

Every data region MUST account for initial loading, success, valid zero data, no matching results, no data yet, partial failure, full failure, stale refreshing data, permission denial, an unsupported schema version, and a part the record does not contain (6.4), as applicable.

Use stable-size skeletons for first load; retain useful data during refresh. Empty states explain what is missing and provide a relevant action. Errors offer a retry only when meaningful. “No results” must not be confused with “failed to load,” and “not in this record” with either.

### 6.4 File-backed, read-only data

The benchmark's results are the first consumer of this baseline, and they are files, not an API: a root directory of immutable, schema-versioned JSON and JSONL documents plus a content-addressed blob store, served statically. The rules below apply to any project whose data looks like that.

- One data-source adapter, with one method per file kind (index, document, rows, blob) over a base URL, is the only module that knows where files live. Local development points it at the producer's output directory; a published site points it at a copied tree.
- Every document names its schema (`"$schema": "<producer>/<kind>/v<n>"`). Gate on it: parse only the kinds and major versions the viewer knows, render an explicit “this viewer does not read <schema>” state for the rest, and never read a field the schema does not promise. Row files are validated per row; a bad row is reported with its line number, not silently dropped with the file.
- Where the producer publishes JSON Schemas, the viewer's types are generated from them and the boundary validates with them (2.3).
- Content-addressed artifacts (`sha256:<hex>`) are immutable: fetch them lazily, cache them for the session by digest, and MAY verify the digest after download. Large artifacts offer a download instead of an inline view above a size the profile sets.
- Aliases (`latest`, a profile name) are resolved through the index document, never through a path. Symlinks do not survive static hosting.
- Row volume decides the rendering path, measured, not guessed. The profile sets a row budget for main-thread parsing and a file-size budget above which a file is not loaded whole in the browser; beyond them, a worker parses and pre-aggregates, and summaries drive the page while rows load on demand and filtered. Before the viewer grows its own aggregate cache, ask the producer for an aggregate file.
- A record that labels its own exactness or validity (`order: inferred`, `exact_step: false`, `reliable: false`, `applied: false`) carries that label into every view that shows it. Derived data is never styled as measured data, and a measurement the producer marks unreliable is shown as such, not hidden.
- Parts are optional: a record may lack a suite, a file or a profile. “Not in this record” is its own page state (6.3), with a pointer to the newest record that has the part. It is neither an error nor an empty result.
- A comparison between records comes from the producer's own diff where one exists and is computed in the viewer only for pairs the producer did not compare. A computed comparison says it was computed.

## 7. Chart standard

- Each chart MUST have a title, units, time range where relevant, and a text summary or accessible data equivalent. Decorative SVGs are hidden from assistive technology.
- Measure the actual container for chart layout. A fixed viewBox is appropriate for a sparkline but is not sufficient for all labeled charts. Use a cleaned-up ResizeObserver hook for responsive chart dimensions.
- Handle empty, one-point, all-zero, constant, negative, non-finite, sparse, and out-of-order data deliberately.
- Decide whether missing points create gaps; never silently connect missing samples or convert missing values to zero.
- Validate and sort timestamp series before rendering. Avoid misleading smoothing; use linear interpolation unless a smoother curve is justified.
- Label axes, units, and legends. Zero-baseline decisions must reflect the chart type and meaning; truncated scales must not conceal magnitude.
- Chart tooltips must not be the sole access to values. Provide keyboard-operable inspection or a nearby data table for interactive charts.
- Large data MUST be aggregated, sampled, or rendered with an appropriate backend after measurement. Preserve extrema and disclose aggregation where relevant.
- Expensive computation MAY move to a Web Worker. D3 DOM work cannot simply move into a worker.
- Use stable keys and stable chart series colors across filters and routes. Do not assign a new meaning to a series color on every refresh.
- Step data stays stepped. A series defined on discrete steps (a budget sweep, a shedding curve) renders with step interpolation, never with a line that implies values between the steps.
- A fitted scaling plot (log-log) shows the fitted exponent, its standard error and r² beside the fit, and the points the fit used. A fit over fewer points than the profile's minimum is labeled as such.
- A matrix (requirement × implementation, reason × slot) encodes the rate in the cell color and the count in the cell text, and puts the numerator and denominator in the cell's accessible name and in the table alternative, so an exercised cell at zero is distinguishable from an unexercised one.
- A percentile comes with its sample count and, when the source has one, its confidence interval. A p50 alone is not a latency.

## 8. Corrected chart blueprint

This intentionally small client component demonstrates the default ownership model. React renders the SVG, D3 computes geometry, and GSAP owns only optional dash-offset motion. It is a sparkline, not a complete interactive analytics chart.

Assumptions: compatible React/TypeScript and GSAP packages, `d3-array`, `d3-scale`, `d3-shape` plus corresponding TypeScript declarations if needed, generated shadcn Card components, and the `@/` alias. The snippet must be typechecked and tested in the target repository before adoption.

```tsx
"use client";

import { useId, useMemo, useRef } from "react";
import { extent } from "d3-array";
import { scaleLinear } from "d3-scale";
import { line } from "d3-shape";
import gsap from "gsap";
import { useGSAP } from "@gsap/react";
import { Card, CardContent, CardHeader, CardTitle } from "@/components/ui/card";

gsap.registerPlugin(useGSAP);

type AnalyticsCardProps = {
  title: string;
  values: readonly number[];
  summary: string; // Human-readable context including units and period.
  animate?: boolean; // Opt in; do not enable for continuously polling cards.
};

export function AnalyticsCard({
  title,
  values,
  summary,
  animate = false,
}: AnalyticsCardProps) {
  const id = useId();
  const rootRef = useRef<HTMLDivElement>(null);
  const pathRef = useRef<SVGPathElement>(null);

  const geometry = useMemo(() => {
    if (values.length === 0) return null;
    // Preserve missing sample positions; line.defined() creates gaps.
    const finite = values.filter(Number.isFinite);
    if (finite.length === 0) return null;
    const [min, max] = extent(finite) as [number, number];
    const padding = min === max ? Math.max(Math.abs(min) * 0.05, 1) : 0;
    const x = scaleLinear()
      .domain([0, Math.max(values.length - 1, 1)])
      .range([8, 312]);
    const y = scaleLinear()
      .domain([min - padding, max + padding])
      .range([88, 8]);
    const makeLine = line<number>()
      .defined(Number.isFinite)
      .x((_, index) => x(index))
      .y((value) => y(value));
    const pointIndex = values.findIndex(Number.isFinite);
    return {
      path: makeLine(values) ?? "",
      point: finite.length === 1
        ? { x: x(pointIndex), y: y(values[pointIndex]) }
        : null,
    };
  }, [values]);

  useGSAP(() => {
    const node = pathRef.current;
    if (!animate || !node || !geometry || geometry.point) return;
    const media = gsap.matchMedia();
    media.add("(prefers-reduced-motion: no-preference)", () => {
      const length = node.getTotalLength();
      if (length <= 0) return;
      gsap.fromTo(
        node,
        { strokeDasharray: length, strokeDashoffset: length },
        { strokeDashoffset: 0, duration: 0.28, ease: "power1.out" },
      );
    });
    return () => media.revert();
  }, {
    scope: rootRef,
    dependencies: [geometry, animate],
    revertOnUpdate: true,
  });

  return (
    <div ref={rootRef}>
      <Card>
        <CardHeader>
          <CardTitle><h2 id={`${id}-title`}>{title}</h2></CardTitle>
        </CardHeader>
        <CardContent>
          <p id={`${id}-summary`} className="text-sm text-muted-foreground">
            {summary}
          </p>
          {geometry ? (
            <svg
              viewBox="0 0 320 96"
              className="mt-4 h-24 w-full"
              role="img"
              aria-labelledby={`${id}-title ${id}-summary`}
            >
              {geometry.point ? (
                <circle
                  cx={geometry.point.x}
                  cy={geometry.point.y}
                  r={3}
                  className="fill-primary"
                />
              ) : (
                <path
                  ref={pathRef}
                  d={geometry.path}
                  className="fill-none stroke-primary stroke-2"
                  vectorEffect="non-scaling-stroke"
                />
              )}
            </svg>
          ) : <p className="mt-4 text-sm">No data available.</p>}
        </CardContent>
      </Card>
    </div>
  );
}
```

The y-domain is deliberately data-relative for this sparkline. Do not reuse it as an unlabeled magnitude comparison chart. The parent must provide immutable values and an accurate summary. Loading, errors, and permissions belong in the parent feature controller.

GSAP's dependency cleanup and media-query teardown are deliberate; the SVG remains visible when animation is disabled. [2]

## 9. Lottie standard

The React export is `DotLottieReact`; acquire the player using `dotLottieRefCallback`, not an assumed `DotLottiePlayer` React ref API. The captured controller exposes methods such as `play()`, `pause()`, `stop()`, and `setFrame()`. Verify the installed runtime's types before implementing advanced playback. [4]

- Use the installed package's controller type or infer the callback parameter type; do not use `any` to bypass an API mismatch.
- Store assets locally or on an approved origin. Review licensing, provenance, network policy, and file size. Do not accept arbitrary user-provided asset URLs.
- Render a static fallback for reduced motion, runtime failure, or unsupported rendering. A success/error label remains meaningful without animation.
- Autoplay/loop MAY be used for decorative assets when appropriate, but nonessential endless motion is not the default. Pause offscreen or hidden-page playback; provide pause controls for persistent motion where needed.
- Hover is not the only interaction. If playback is user-controlled, use a real button with an accessible name and equivalent keyboard behavior.
- Decorative players use an `aria-hidden` wrapper. Meaningful status uses adjacent text; do not announce every frame.
- GSAP-driven scrubbing and autonomous player playback MUST NOT compete. Wait for player readiness before frame operations and clean up controller listeners and timelines.
- Reserve Lottie for illustration. Use Lucide for routine static icons and CSS for a lightweight spinner.

## 10. Accessibility and behavior

Target WCAG 2.2 AA. This is a quality target, not a claim of certification.

- Provide a skip link, named navigation regions, one primary main region, logical headings, and meaningful document titles.
- All actions must be keyboard reachable with a visible focus indicator. Preserve native button/link behavior.
- Test text contrast, non-text UI contrast, dark mode, forced-colors behavior, zoom, and screen reflow. Do not assume generated components guarantee full application accessibility.
- Use a comfortable 44 px touch-target design target where feasible; dense interfaces must still satisfy applicable minimum target-size requirements or documented exceptions.
- Dialogs and mobile navigation preserve focus management, Escape behavior, accessible names, and focus restoration. Do not override primitive behavior with animation code.
- Reduced motion removes nonessential entrance, parallax, scrub, and looping effects. It does not remove essential feedback or meaningful state changes.
- Long-lived status changes use restrained live announcements. Do not announce every poll or repaint.
- Do not expose essential actions only on hover. Respect disabled, loading, read-only, and permission-denied distinctions.
- Confirm destructive operations with clear scope and consequence. Prefer undo where safe and practical.

## 11. Performance and security

- Establish performance budgets in the project profile using representative data and supported devices. Measure bundle cost, interaction latency, rendering, memory, and route transitions.
- Lazy-load optional animation and visualization modules where useful. Avoid importing all of D3 solely for scales and one path generator.
- Do not animate every table row, metric, or polling update. Stop hidden animation and clean up chart simulations.
- Keep server-only secrets and authorization logic off the client. Enforce access on the server; navigation filtering is presentation only.
- Never inject untrusted HTML or unsanitized SVG into the DOM. Validate URLs and user-supplied content at the correct boundary.
- Do not log credentials, personal records, or raw sensitive response payloads. Errors and telemetry must be redacted.
- SSR projects keep browser APIs, observers, GSAP, and players behind appropriate client boundaries. Do not disable SSR for the entire application to fix one browser-only component.
- Theme and sidebar persistence must avoid hydration mismatches and an unnecessary theme flash.

## 12. Repository organization

Adapt names to the chosen framework without changing the boundaries.

```text
src/
  app/ or routes/          # Routing and framework entry points
  components/
    ui/                    # Generated and maintained shadcn primitives
    layout/                # DashboardShell, AppSidebar, AppHeader
    dashboard/             # PageHeader, FilterBar, MetricCard, state panels
    charts/                # Chart frames and shared renderers
  features/<feature>/
    api/                   # Query keys, requests, schemas, adapters
    model/                 # Domain types and pure selectors
    components/            # Feature-specific presentation
  hooks/                   # Media query, resize, shared lifecycle helpers
  lib/                     # Formatting, API client, theme adapters, cn
  styles/                  # Global stylesheet and token extensions
public/animations/         # Reviewed optional assets
 docs/
  design/project-profile.md
  adr/
```

In this repository the UI lives in `ui/` at the repository root, beside `domain1/`, with one feature module per benchmark domain (`features/d1/`), so a later domain adds a module rather than a second application.

Feature components MUST NOT become a dumping ground for unrelated global utilities. Shared components must have a concrete repeated use case. Prefer composition over a giant dashboard component with dozens of boolean props.

## 13. Agent implementation workflow

1. Inspect the repository, lockfile, framework, generated shadcn APIs, existing tokens, and project profile. Do not assume an empty project.
2. Declare the page's task, data contract, state owner, required states, permissions, and responsive behavior.
3. Reuse the shell and existing primitives. Implement static semantics and layout first.
4. Implement validation, data adapters, filtering, formatting, and state behavior.
5. Add chart geometry with edge-case tests. Confirm React/D3 ownership explicitly.
6. Add optional motion only after the page works without it. Verify reduced motion and resource cleanup.
7. Run formatting, lint, type checks, tests, build, and representative browser checks. Report unrun checks honestly.
8. Update the profile or decision record for new dependencies and deliberate deviations.

Agents MUST NOT introduce packages, modify authentication behavior, rewrite routing, or change generated component APIs merely to make a visual example work. Never claim code was tested unless the checks actually ran.

## 16. Adoption and maintenance

For existing repositories, first inventory the actual stack, adopt the profile, and fix correctness/accessibility issues. Extract the shared shell next; consolidate tokens and data ownership after that. Migrate motion and chart rendering feature by feature. Avoid a big-bang rewrite.

For future repositories, create a template repository after this baseline is validated in one real application. Include the shell, token setup, required state components, formatting helpers, tests, CI, and a filled example profile. Copying this document alone does not install or configure the stack. The first adopter is this repository's results UI, so the template waits until that UI exists.

Documentation evidence is cited inline as [n] and listed in section 18. Uncited defaults are proposed project policies, not guarantees of a library's behavior. Recheck official documentation when adopting or upgrading packages.
